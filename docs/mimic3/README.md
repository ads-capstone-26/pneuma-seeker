# MIMIC-III data preparation

This folder documents how the MIMIC-III dataset is prepared for this project, and holds the **shared
results** that everyone uses. You do not need to know the rest of the project to follow it; terms are
explained at the end.

How the pipeline is built, where its description of the tables (the schema) comes from, how to set it up
for a different dataset, and the formats of the result files are explained in the developer guide:
[`src/pneuma_seeker/services/core/data_prep/README.md`](../../src/pneuma_seeker/services/core/data_prep/README.md).

## What this is for

The project answers questions about patient data by writing database queries (SQL). Before it can do
that reliably, the data must be loaded correctly and its problems must be known: a query that ignores,
say, duplicate rows or codes stored with extra spaces gives a wrong answer without any error. This
pipeline therefore:

1. checks that the raw files are complete,
2. loads them into a local database with the correct data types,
3. measures data problems and turns each one into a **query convention**, a plain-language rule such as
   *"Identify in-hospital death with `admissions.hospital_expire_flag = 1`, not by testing `deathtime`
   against the admission window"*, which the query system follows when it writes SQL,
4. describes every table and column (the **schema profile**) so the query system can find the right
   tables, columns and links for a question.

The data themselves are never edited, because benchmark questions and their reference answers are
written against the original data.

```
your MIMIC-III files ─inventory─> checked file list ─load─> local database ─quality─> ─profile─> local reports
                                                                  │                                   │
                                                                  │                         publish (maintainer)
                                                                  │                                   ▼
                                                                  └──────> query system <──── docs/mimic3/ (shared)
```

## Files in this folder

| File | What it is |
|---|---|
| `README.md` | This guide. |
| `mimic3_query_conventions.json` | The query conventions, each with its evidence (counts), and the **data fingerprint** they were derived from. Read by the query system. |
| `mimic3_data_quality_report.md` | The readable data quality report behind those rules. |
| `mimic3_schema_profile.json` | Every table and column: meaning, type, role, missing values, common values, links to other tables and the rules that apply. Read by the query system. |

**Do not edit the result files by hand.** They are regenerated by the dataset maintainer (below).

## Setup (once)

1. **Get the data.** Get access to MIMIC-III v1.4 through PhysioNet (credentialed access, see Terms) and keep
   your copy of the CSV files (`.csv` or `.csv.gz`, one per table) in a folder on your machine.
2. **Get the code** and open a terminal in the project folder (`pneumaRX`):
   ```
   git clone <repository-url>
   cd pneumaRX
   ```
3. **Create the Python environment** (with [Miniconda](https://www.anaconda.com/docs/getting-started/miniconda/install/overview)):
   ```
   conda create --name pneuma_seeker python=3.12.12 -y
   conda activate pneuma_seeker
   pip install -r requirements.txt
   ```
   The data preparation itself only needs `duckdb` and, for the tests, `pytest`
   (`pip install duckdb==1.4.2 pytest`). Run `conda activate pneuma_seeker` in every new terminal.
4. **Tell the pipeline where the data are.** Copy `.env.example` to `.env` if you have no `.env` yet
   (`cp .env.example .env`), then set this line in `.env`:
   ```
   MIMIC_III_DIR=/path/to/your/MIMIC_III
   ```
   `.env` is never committed, so your path stays on your machine. You can also pass
   `--mimic-dir /path/to/MIMIC_III` on the command line. There is no default: if the folder is not set,
   the pipeline stops and explains how to set it.
5. **Check the installation** with the tests (made-up data only, a few seconds):
   ```
   PYTHONPATH=src python -m pytest tests/services/core/data_prep --noconftest -q
   ```
   Every test should pass.

## Running it

From the project folder:

```
python scripts/prepare_mimic3.py inventory   # a few seconds
python scripts/prepare_mimic3.py load        # several minutes
python scripts/prepare_mimic3.py quality     # a few minutes, read-only
python scripts/prepare_mimic3.py profile     # a few minutes, read-only; needs the quality results
python scripts/prepare_mimic3.py all         # the four stages above, in order
python scripts/prepare_mimic3.py publish     # dataset maintainer only
```

Each stage prints what it does and why before it starts. A new user normally runs `all` once; run `load`
again only when the source files change, and `quality` / `profile` after any change to the checks.

## Checking that it worked

| Stage | Looks right when | If not |
|---|---|---|
| `inventory` | every table you have shows `ok`; the 5 tables missing from the team's copy show `absent (known)` | `MISSING`: file not found or misnamed (names must be `TABLE.csv` or `TABLE.csv.gz`). `HEADER MISMATCH`: the file's columns differ from the official list; check the file came from MIMIC-III v1.4 |
| `load` | every table `ok`, `tables needing attention: none` | `COUNT DIFFERS` or `REJECTED ROWS`: the file is incomplete or damaged; download it again |
| `load`, `quality` | `Local data match the shared snapshot (fingerprint ...)` | `WARNING: your local MIMIC-III data differ ...`: your copy differs from the one the shared results describe; the warning lists the tables. Re-download them or ask the maintainer which copy is current |
| `quality` | `errors 0`; flagged checks are expected (they become rules) | `ERROR`: a check failed to run; report it with the console output |
| `profile` | a line `Profiled N tables, M columns, K links` | `No data quality results yet`: run `quality` first |

Your local reports (one JSON per stage, exact counts, never committed) are in `data_src/mimic_iii/reports/`.

## The stages

### 1. Inventory: are the files complete?

For each of the 26 official MIMIC-III tables, looks for `TABLE.csv` or `TABLE.csv.gz` and compares its
first line (the column names) with the official column list. A missing, misnamed or differently structured
file is reported before anything is loaded. Only file names, sizes and column names are read.

### 2. Load: put the data in a database with the right types

Loads every table that passed the inventory into a local DuckDB database. Every column gets its official
type: codes such as ICD-9 diagnosis codes are text (so `'0066'` keeps its leading zeros instead of becoming
the number 66), and times are timestamps. Lines that cannot be read are counted, not silently skipped, and
each table's row count is compared with the published count. A full rebuild only replaces the old
database once every table has loaded.

### 3. Quality: measure the problems

Asks the loaded database a set of questions, each answered with two numbers: how many rows have the
problem (`flagged`) and how many were checked (`total`).

| Group | Question asked |
|---|---|
| Keys and duplicates | Is each identifier unique where it should be? Are rows repeated? |
| Links between tables | Does every patient, admission, ICU stay, item or code referred to in one table exist in the table that defines it? |
| Time order | Do end times follow start times? Do events fall inside their hospital admission? Are the death fields consistent? |
| Known MIMIC-III behaviours | How codes are stored, which ICU system recorded what, missing codes, rows marked as errors, and gaps in this copy of the data. |

It also measures missing values per column, text values with extra leading or trailing spaces, and the
values used in coded columns. Each check gets a status: **pass** (expected none, found none), **flag**
(expected none, found some) or **info** (a count with no single correct value).

### 4. Profile: describe every table and column

Combines the written description of each table and column (from the MIMIC-III documentation, kept in
`src/pneuma_seeker/services/core/data_prep/mimic3_docs.py`) with facts measured on the loaded data:

- **per table**: description, number of rows, key column, and kind (*core*: patients, admissions, ICU
  stays; *event*: things that happened to a patient; *dictionary*: lookup lists of codes and items);
- **per column**: type, **role** (identifier, reference to another table, code, time, flag, category,
  number, text, always empty, ...), share of missing values, approximate number of distinct values, the
  values of category columns, which table it links to, and which query conventions apply to it;
- **links between tables**: every documented join, with how many rows were checked and how many found no
  match (from the quality stage).

The query system searches this when it maps a question to tables and columns, so it knows not only what a
column means but how it behaves in this copy of the data.

### 5. Publish: write the shared results (dataset maintainer only)

Re-runs the quality checks and the profile and writes the shared files in this folder, made safe and
stable to commit:

- **Data fingerprint instead of a date.** The files are stamped with the row count of every table and a
  short code derived from them. They change only when the data or the rules change, so `git diff` shows
  only real changes.
- **Small counts hidden.** Every count from 1 to 10 is written as `<11` and its percentage left out,
  following the common "rule of 11" for health data, and category values seen in fewer than 11 rows are
  left out of the profile. (Counts that could be worked out by subtraction are not hidden.)
- **No file paths or user names.**

One person, the **dataset maintainer**, runs `publish`, reviews the changes with `git diff docs/mimic3/`
and commits them. Everyone else uses the files as they are.

**If your data differ.** `load` and `quality` compare your local database with the fingerprint and print a
warning listing the tables whose row counts differ or are missing. The shared rules may then not describe
your data; re-load from the shared source or ask the maintainer which copy is current. The query system
can run the same check (`compare_with_snapshot`; see the developer guide).

## Data protection

MIMIC-III may only be used under its data use agreement. The pipeline reads and writes files on your
machine only, never sends data to a language model or web service, and prints or writes only column names
and aggregate counts, never values about individual patients. Rows that fail to load are counted, and their
contents are discarded. Only the shared results in this folder, with small counts hidden, are committed.

## Known limitations of the team's copy

The team's copy has 21 of the 26 tables. CHARTEVENTS, INPUTEVENTS_MV, LABEVENTS, NOTEEVENTS and
OUTPUTEVENTS are missing, so questions about laboratory results, charted vital signs, ICU fluid inputs
recorded after 2008, fluid outputs and clinical notes cannot be answered. The quality report measures the
effect (for example, how many ICU stays have no fluid-input data).

## Terms

- **MIMIC-III v1.4**: a freely available but access-controlled database of de-identified records of about
  46,500 patients admitted to intensive care at Beth Israel Deaconess Medical Center, Boston, 2001-2012.
- **PhysioNet, data use agreement (DUA)**: PhysioNet distributes MIMIC-III to credentialed researchers who
  sign an agreement that, among other things, forbids sharing the data.
- **Table, row, column**: MIMIC-III is a set of tables (e.g. PATIENTS, ADMISSIONS); each row is one record
  (a patient, an admission, a lab measurement); each column is one field of it.
- **Identifier / key**: a column that names a record, e.g. `subject_id` (patient), `hadm_id` (hospital
  admission), `icustay_id` (ICU stay). Tables are linked ("joined") through these keys.
- **SQL, query**: the language used to ask a database a question, e.g. "how many admissions ended in death".
- **DuckDB**: the database program used to store the data locally (a single file, no server).
- **ICD-9**: the coding system for diagnoses and procedures used in MIMIC-III, stored without the dot
  (`4019` means 401.9).
- **CareVue / MetaVision**: the two ICU record systems used in 2001-2008 and 2008-2012; some ICU data are
  stored in different tables depending on which system recorded them.
- **Query convention**: a rule derived from a data quality finding that says how to write queries so the
  finding does not distort the answer.
- **Schema profile**: a description of every table and column of a database, here combined with
  measurements such as missing values and common values.
- **Data fingerprint**: the row count of every table plus a short code computed from them; two copies of the
  data with the same fingerprint have the same tables and sizes.
- **Dataset maintainer**: the one person who regenerates and commits the shared results.
